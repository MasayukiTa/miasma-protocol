Current state (as of this investigation, 2026-09-04):
- The crypto/bypass-design layer (BBS+, AEAD, onion routing) has been reviewed separately and is solid.
- The actual content-transfer layer has serious, previously-undiagnosed gaps that undermine the project's core "censorship-resistant" claim:
  - `dissolve_and_publish` currently makes the publishing node the sole holder of every shard. There is no distribution to other peers. Taking the publisher offline makes its content unavailable -- no better than a regular server.   - `StreamingRetrievalCoordinator` (100GB files, ~64MiB peak RAM, fully implemented, fully tested in isolation) is never called from the real coordinator/daemon/CLI retrieve path. Retrieval always buffers the whole reconstructed file in memory.

## External design review (2026-09-04, codex 5.6 sol + claude fable)

Both reviewers were given the original 2.1 design (enum-extend `/miasma/share/1.0.0`, `connected_peers()`-based target selection, `NetworkShareSink` with a `Mutex<HashMap<slot_index, ShardLocation>>` side-channel) and asked the same 5 questions. Both agreed the design as sketched should not ship; both independently found real bugs by reading the actual source, not just reasoning abstractly. Two claims were independently code-verified by the orchestrating session itself before trusting either reviewer's conclusions: `connected_peers()` (`network/node.rs` `GetConnectedPeers` handler) really does return `Vec::new()` for every peer's addrs today ("No addresses needed -- peer is already connected/dialed") -- the original `NetworkShareSink` design could not have worked, full stop.

**Where both agreed (adopted as blocking requirements for 2.1):**
- Publishing must never silently succeed with fewer than `data_shards` distinct remote-acknowledged shard placements per segment -- that would produce a normal-looking, unrecoverable-without-the-publisher DHT record, defeating the entire point of this phase. Local/publisher copies are always kept in addition to remote copies (redundancy, not a replacement for the fix); a below-threshold remote-distribution attempt returns a typed `InsufficientRemotePlacements`-style error/report rather than `Ok(mid)`.
- Add a **separate** new protocol (`/miasma/share-store/1.0.0`) rather than enum-extending the existing `/miasma/share/1.0.0` pull protocol -- the existing fetch structs are deserialized verbatim across five transport paths (WSS, obfuscated QUIC, Tor/shadowsocks docs, onion, direct payload), so "enum-extend" is not a local libp2p change; a separate protocol also gives free push-capability detection via negotiation and lets push/pull have different rate limits and size caps.
- Inbound `Store` acceptance must be gated on the sender being an admission-`Verified` peer (`peer_registry`/`admission_policy.rs`), not just passing `coarse_verify` (which only proves self-consistency of whatever bytes the sender sent, not authorization) -- unauthenticated storage plus the existing store's flat LRU-eviction quota is a real destructive-DoS vector (a connected attacker can push junk that evicts other legitimately-hosted shares). This is genuinely cheap here, not scope creep: `peer_registry`/`routing_table` already live in the swarm task, so the gate is a single `is_verified()` check plus routing-informed selection, not new admission infrastructure.
- Target selection must not be "any connected peer" or "always the single best-ranked peer": use verified peers only, filtered/ranked via the existing `routing.rs` reliability + IP-prefix-diversity machinery, with a per-holder shard cap (no holder should exclusively hold more than `n - k` of a segment's shards) and randomization among eligible candidates -- both reviewers flagged that Shamir shares are a **confidentiality** control too (an attacker who ends up holding `k` shares of key material can reconstruct content), so selection is a security-relevant choice, not just a load-balancing one.
- Replace the `Mutex<HashMap<slot_index, ShardLocation>>` + `take_locations()` side-channel with a proper `ShareSink::store()` return type carrying real placement metadata directly (both converged on an associated `type Receipt`, resolved as free once Fable found there is **no production `ShareSink` impl today** -- only two test sinks in `distributor.rs` -- so widening the trait costs nothing production-facing).
- Fix the pre-existing `shard_index`-only location lookups (ignoring `segment_index`) that are harmless today only because every segment happens to live on the same single publisher -- codex found `network/coordinator.rs`, Fable additionally found the same bug in `transport/payload.rs`.

**Where Fable specifically improved on codex's version (adopted):**
- Rather than adding a new swarm-side "give me addresses for these candidate peers" command, have the **holder report its own advertised addresses in the `Store` ACK** (`Accepted { address, advertised_addrs }`) -- the holder is the only real authority on its own reachability, and this avoids needing address-lookup plumbing at candidate-selection time at all.
- Do **not** add a `share_id` field to `ShardLocation`/`DhtRecord` in this phase (codex's suggestion) -- these are bincode-serialized, not self-describing/versioned-field-tolerant like JSON with `#[serde(default)]`; adding a field would break every already-installed node's record parsing. The cheaper fix for generation ambiguity: a `Store` for an existing `(mid, segment_index, slot_index)` tuple *replaces* the existing entry rather than coexisting with it, sufficient while a DHT record only ever points at the latest generation.
- Found a **live, pre-existing** version of the "generation ambiguity" bug independent of the repair path: `encrypt()` draws a fresh random key every call while MID is content-derived, so publishing the *same file twice* on one node today already produces two incompatible `(mid, seg, slot)`-tuple generations colliding in one store -- a better, simpler repro than codex's repair-path framing, and useful as the actual test trigger.
- Flagged a real gap neither the original design nor codex raised: **direct share-push reveals the publisher's real PeerId to every chosen holder** (retrieval already has onion/relay routing; push has none) -- to be written down explicitly as a known Phase 2.1 limitation, not silently discovered later.
- On LocalShareStore concurrency: the store's own doc comment says it isn't `Sync` and must be externally locked, yet it's already shared as `Arc<LocalShareStore>` with no synchronization around its index read-modify-write -- fine with exactly one writer (today), a real race the moment inbound `Store` becomes a second writer. Fable's fix (an internal mutex around the index RMW) is right-sized; a full serializing actor (codex's suggestion) is overkill for this phase.

**Explicitly deferred as documented follow-ups, not blockers** (both reviewers' more ambitious items): true Kademlia K-closest placement (vs. verified-connected-peer pool), fetch/audit-based holder reputation, storage retention leases, a repair-scheduler trigger wired to `needs_repair`, `share_id`-based fetch (a `/miasma/share/2.0.0` protocol bump), chunked/Merkle-rooted DHT records for very large placement lists, a full v1/v2 mixed-fleet interop test.

**Test gate adopted for 2.1** (refined from codex's 9 down via Fable's cuts/rewrites): (1) every segment reaches >=`data_shards` distinct remote-acknowledged holders; (2) publisher shuts down, a node that *never connected to the publisher* retrieves successfully using only the propagated DHT record's holder addresses (the actual regression test for the phase's whole point); (3) one representative "shut down a holder, retrieval still works via the others" case; (4) fewer than `data_shards` remote accepts returns the typed insufficient-placement result, no normal record published; (5) `Store` from a non-`Verified` peer is rejected; (6) `Store` from a `Verified` peer while the hosted-share budget is full is rejected without evicting any owned/previously-hosted share; (7) multi-segment content placed across different holders retrieves the correct bytes per segment; (8) publishing the same file twice does not corrupt or ambiguously mix generations on retrieval.
